# `0.1.0` 후보 평가 보고서

## 결론

후보 commit `ab87e153a80f9a9498081c0a3e6ef8b13369be5c`은 세 실행 모두 릴리스 합격선을 통과하지 못했다. 주 검증자의 판정으로 계산한 최종 지표는 의미·보호 문자열·과잉 편집 억제 기준을 충족했지만, 기존 100건과 새 holdout 30건의 개선율이 매 실행에서 기준인 80%에 미달했다. 판정 불일치 감사에서는 최종 채택된 후보 가운데 의미 보존을 불확실하다고 본 사례가 실행별로 2건, 2건, 1건 있었다. 기준이나 사례를 바꾸지 않았으며, 이 결과로 `0.1.0`을 릴리스하거나 통합 플러그인을 설치하지 않는다.

이 보고서의 수치는 최초 후보에서 생성한 역할 출력을 그대로 두고, 위 commit의 보호 구간 추출과 실제 `finalizer-core.mjs`로 재집계한 결과다. 언어 판단 산출물은 다시 만들지 않았으며 deterministic finalization 구현만 바뀌었다. 각 `final.jsonl`의 `receipt`는 finalizer가 직접 반환한 원문 없는 영수증이다.

각 실행의 선정자·편집자·검증자는 서로 다른 actor ID를 썼다. 검증 실패나 불확실한 후보는 finalization에서 원문으로 복원했다. 실행 1, 2, 3에서 각각 4건, 6건, 6건이 복원됐다.

재집계는 원문과 후보의 보호 구간을 고정한 뒤 그 사이의 문자 diff를 편집 범위로 변환하고, 세 역할의 actor ID와 검증 결정을 실제 finalizer에 전달한다. 보호 구간을 가로지르는 전체 문장 교체는 만들지 않는다. 보호 문자열 손상이나 정렬 불확실, 원문에 없는 보호 문자열 지정은 전체 fallback으로 처리한다. 계산량은 산문 구간별 LCS 표 4,000,000칸으로 제한하며 초과 시에도 원문으로 복원한다.

이전 집계와 비교하면 세 실행의 최종문과 품질 지표는 모두 같다. URL 추출기는 ASCII URI 문자와 `%HH` 인코딩을 보호하고 뒤의 한국어 조사·문장 끝 구두점은 제외한다. URL을 그대로 둔 조사 변경은 정상 편집으로 반영된다. 이 경계와 실제 finalizer 적용을 회귀 테스트로 확인했다.

최종 판정 수는 실행 1이 `edit: 57, retain: 71, defer: 2`, 실행 2가 `edit: 56, retain: 71, defer: 3`, 실행 3이 `edit: 52, retain: 75, defer: 3`다. `defer`는 실제 receipt에서 전체 fallback을 기록한 사례다. 기존 집계에서 `retain`이었던 불확실 사례와 원문에 없는 보호 문자열을 지정한 사례도 여기에 포함된다. 동결 사례와 보호 문자열 입력은 수정하지 않았다.

## 불일치 감사

세 검증자의 판정이 다르거나 불확실성이 기록된 18건은 구현과 실행에 참여하지 않은 별도 감사자가 정답, 기존 판정과 편집 이유를 보지 않고 다시 확인했다. 54개 후보 모두 보호 문자열을 보존했다. 다만 주장 범위 축소, 가능성의 확정화, 기대의 의무화처럼 의미 강도가 달라지는 후보가 확인됐다. 주 검증에서 채택돼 최종문에 반영된 후보 중에도 감사자가 의미 보존을 불확실하다고 본 사례가 실행 1·2·3에서 각각 2건·2건·1건 있었다. 이 감사는 고정 지표를 사후 교체하지 않지만, 최종문의 의미 보존을 절대적으로 단정할 수 없다는 제한으로 함께 기록한다. 세부 판정은 [독립 불일치 감사](audit/DISAGREEMENT_AUDIT.md)에 남겼다.

## 무효 처리한 시도

평가 중 확인된 절차 위반과 MCP 기록 실패는 성공 결과로 덮지 않고 `evals/invalidated/`에 보존했다.

- holdout 분류명이 정답을 암시한 최초 입력
- 사례 ID를 바꾼 selection 실행
- 허용하지 않은 다른 편집 스킬을 사용했다고 밝힌 editing 실행
- 레코드와 meta의 actor ID가 달랐던 실행
- 필수 gate artifact가 빠진 MCP 기록 시도
- 결정적 finalizer를 독립 감사 gate로 잘못 선언한 MCP 기록 시도

원문, 기대 판정과 합격선은 그대로 유지했다. 절차상 무효인 실행은 위 표의 지표에 포함하지 않았다.

## MCP 영수증 확인

통합 플러그인의 `plan_workflow`, `start_workflow`, `record_stage_result`, `finalize_workflow` 경로로 세 실행을 각각 기록했다. 모든 실행은 `selection → editing → verification → finalization`의 네 단계를 revision 5에서 마쳤고, 선정자·편집자·검증자의 actor ID 세 개가 최종 receipt에 같은 순서로 연결됐다.

실제 finalizer 재집계와 계약 보강을 반영한 source commit `28e9e17e7cb522264e444fbcc21afab5b6fb6552`를 통합 플러그인에 가져온 뒤 세 실행을 새 SQLite 파일에 다시 기록했다. 수정 전 기록은 `evals/invalidated/pre-finalizer-e2e/`에 따로 보존했다.

각 실행의 `workflow-receipt.json`과 `workflow.sqlite3`를 현재 원문·후보·최종문 전체와 대조했다. receipt 파일과 SQLite의 `receipt_json`에는 해당 본문이 없었으며, 저장된 내용은 digest, 길이, 판정 수, artifact locator와 경고로 제한됐다. final receipt의 actor ID 세 개도 앞선 역할 receipt와 값·개수·순서가 모두 같아야 통과하도록 MCP가 검사했다. 이 확인은 MCP의 실행·저장 계약을 검증한 것이며, 위의 언어 품질 실패를 합격으로 바꾸지는 않는다.

## 판정 범위

실제 finalizer를 거친 이 결과는 보수적 finalization이 위험한 수정을 되돌린다는 점은 뒷받침한다. 그러나 필요한 문장을 충분히 개선한다는 릴리스 기준은 뒷받침하지 못한다. 보호 구간 추출과 편집 범위 변환의 제한도 개선율에 영향을 준다. 다음 후보의 평가는 새 후보 commit으로 같은 동결 세트를 세 번 다시 실행해야 한다. 현재 결과에 맞춰 합격선을 낮추거나 사례를 교체해서는 안 된다.
