# `0.1.0` 후보 평가 보고서

## 결론

후보 commit `d8ffc6d730dd89b035ba3290033e6432ac960e19`은 세 실행 모두 릴리스 합격선을 통과하지 못했다. 최종문에서는 의미와 보호 문자열을 안전하게 보존했고 과잉 편집도 억제했지만, 기존 100건과 새 holdout 30건의 개선율이 매 실행에서 기준인 80%에 미달했다. 기준이나 사례를 바꾸지 않았으며, 이 결과로 `0.1.0`을 릴리스하거나 통합 플러그인을 설치하지 않는다.

## 불일치 감사

세 검증자의 판정이 다르거나 불확실성이 기록된 18건은 구현과 실행에 참여하지 않은 별도 감사자가 정답, 기존 판정과 편집 이유를 보지 않고 다시 확인했다. 54개 후보 모두 보호 문자열을 보존했다. 다만 주장 범위 축소, 가능성의 확정화, 기대의 의무화처럼 의미 강도가 달라지는 후보가 확인됐다. 이 감사는 불일치의 원인을 확인하는 보조 근거이며 전체 성능 지표를 대체하거나 릴리스 실패를 번복하지 않는다. 세부 판정은 [독립 불일치 감사](audit/DISAGREEMENT_AUDIT.md)에 남겼다.

## 무효 처리한 시도

평가 중 확인된 절차 위반과 MCP 기록 실패는 성공 결과로 덮지 않고 `evals/invalidated/`에 보존했다.

- holdout 분류명이 정답을 암시한 최초 입력
- 사례 ID를 바꾼 selection 실행
- 허용하지 않은 다른 편집 스킬을 사용했다고 밝힌 editing 실행
- 레코드와 meta의 actor ID가 달랐던 실행
- 필수 gate artifact가 빠진 MCP 기록 시도
- 결정적 finalizer를 독립 감사 gate로 잘못 선언한 MCP 기록 시도

원문, 기대 판정과 합격선은 그대로 유지했다. 절차상 무효인 실행은 위 표의 지표에 포함하지 않았다.

## MCP 영수증 확인

통합 플러그인의 `plan_workflow`, `start_workflow`, `record_stage_result`, `finalize_workflow` 경로로 세 실행을 각각 기록했다. 모든 실행은 `selection → editing → verification → finalization`의 네 단계를 revision 5에서 마쳤고, 선정자·편집자·검증자의 actor ID 세 개가 최종 receipt에 같은 순서로 연결됐다.

각 실행의 `workflow-receipt.json`과 `workflow.sqlite3`를 실제 원문·후보·최종문 전체와 대조했다. receipt 파일과 SQLite의 `receipt_json`에는 해당 본문이 없었으며, 저장된 내용은 digest, 길이, 판정 수, artifact locator와 경고로 제한됐다. 이 확인은 MCP의 실행·저장 계약을 검증한 것이며, 위의 언어 품질 실패를 합격으로 바꾸지는 않는다.

## 판정 범위

이 결과는 보수적 finalization이 위험한 수정을 되돌린다는 점은 뒷받침한다. 그러나 필요한 문장을 충분히 개선한다는 릴리스 기준은 뒷받침하지 못한다. 다음 후보를 만들려면 selection과 editing 정책을 수정한 뒤 새 후보 commit으로 같은 동결 세트를 세 번 다시 평가해야 한다. 현재 결과에 맞춰 합격선을 낮추거나 사례를 교체해서는 안 된다.
